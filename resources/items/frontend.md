## Rules

- Apply React, Inertia, Wayfinder, and shadcn conventions where those tools are already installed. This item adds guidance, not frontend packages or an Inertia requirement for API-only applications.
- Keep each domain's pages, components, hooks, and `types.ts` under `resources/js/pages/{domain}/`. Move a component, hook, helper, or type into shared `resources/js/{components,hooks,lib,types}` only when a second domain uses it.
- Page names follow the rendering controller method (`index`, `show`, `create`, `edit`), with nested resources in subfolders. A single-action controller's page follows its controller name; preserve Fortify's established `auth/*` names. The `Inertia::render()` name matches the page file path.
- Page types mirror the output PHP Resources they receive: one type per Resource, named without `Resource`, with matching camelCase fields, nullability, and collection shape. Keep input Data and private model attributes out of frontend props.
- Preserve the application's working layout selection, nesting, and breadcrumb mechanism. Pages default-export their component, declare `type Props`, and set a `Head` title where Inertia is used. Other components use named exports; component files use kebab-case and hooks use `use-*.ts`.
- Use installed Wayfinder route/action exports for internal URLs and submissions. Use an Inertia form API supported by the installed version; a `.form()` variant must exist before it is used. Keep generated routes and application-specific UI composition separate from generated shadcn primitives.
- Add stable `data-test` selectors where automated tests need them, preserve accessible labels and form errors, and keep pending states visible. Use the existing flash mechanism for useful feedback after deliberate changes; do not show an automatic toast for every write or background request.

Use the `laracanon-frontend` skill for implementation in the application's installed stack.

## Skill

This is a **Laracanon-authored implementation workflow** for an existing React/Inertia frontend with optional Wayfinder and shadcn support. It adds no dependencies. Apply each tool-specific step only when that tool is installed; keep another existing frontend or an API-only application on its established stack.

1. Inspect the application's instructions, `package.json`, lockfile, Composer requirements, page resolver, layouts, route generation, shared props, and nearby pages. Verify installed versions before selecting APIs. Read the matching official documentation and installed adapter types/source. Inertia 3 documents its [form APIs](https://inertiajs.com/docs/v3/the-basics/forms), [layouts](https://inertiajs.com/docs/v3/the-basics/layouts), and [flash data](https://inertiajs.com/docs/v3/data-props/flash-data); use the matching documentation for an older adapter without upgrading it for this convention.
2. Trace the controller's Resource props and rendering name to the page. Place domain-owned pages, components, hooks, and `types.ts` together; choose method-based page names and nested folders matching the existing resolver. A web CreateUser operation may render `users/create`; use the real application's route and controller rather than inventing an extra endpoint. Keep a reusable piece local until a second domain actually needs it.
3. Declare `type Props` from the received Resources and page metadata. Remove the `Resource` suffix from the frontend type name, for example `UserResource` becomes `User`, and match its selected camelCase fields and nullability. Read the actual serialization and collection shape instead of deriving a type from Eloquent or input Data. Keep existing shared props separate from domain props.
4. Reuse the established layout and breadcrumb path. If layout selection already uses a page-name prefix in `createInertiaApp`, add only the needed case there; if it uses per-page layouts or a resolver, preserve that mechanism. Inertia 3 supports both a default `layout` callback and per-page layouts, with per-page layouts taking precedence. Do not overhaul `resources/js/app.tsx`, providers, or unrelated pages to implement one screen. Add the page's `Head` title and breadcrumbs through the existing typed metadata API.
5. Inspect the actual generated Wayfinder exports and regeneration configuration before importing from `@/routes/...` or `@/actions/...`; preserve configured paths and regenerate through the existing workflow when routes change. The official [Wayfinder documentation](https://github.com/laravel/wayfinder#conventional-forms) makes form variants opt-in with `--with-form`. Use `<Form {...store.form()}>` only when that generated variant exists. A supported Inertia version can instead use `<Form action={store()}>` or submit the generated route object with `useForm`; verify the installed export and adapter signature first. If Wayfinder is absent, use the application's existing routing integration without installing it as a side effect.
6. Build the form with the application's components, accessible labels, field errors, pending state, and input names matching the FormRequest. Keep normalization and authorization on the server's established request/Data boundary. Reuse existing shadcn primitives and add new primitives through the configured CLI when needed; preserve local UI customizations and put domain-specific composition in the domain folder. Follow existing exports and file naming, and add stable selectors only to elements tests exercise.
7. Keep web and API response behavior distinct at the caller boundary. An Inertia form follows the web redirect and validation flow; it does not consume the API envelope as an Inertia page. A client calling an API reads the `api-responses` contract and its real status. For deliberate web changes, use the existing feedback mechanism when useful. Inertia 3 provides `Inertia::flash()` and client flash APIs; older applications may expose session flash through shared props. Inspect the existing producer/consumer pair and avoid adding duplicate listeners or replaying success toasts on navigation. Background writes need no automatic feedback.
8. Run the application's existing type, lint, build, and focused page/browser checks. Verify Resource field alignment, layout/breadcrumb preservation, generated route imports, pending/error behavior, deliberate feedback, and responsive/keyboard interactions. Report which checks actually ran; a successful build alone does not verify browser behavior.
